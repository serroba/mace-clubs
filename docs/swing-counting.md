# Mace swing counting

## Algorithm

Mace swings are counted from the gyroscope, not the accelerometer. Clubs and
the bulava still use the older accelerometer detector (`SwingCounter.defaultCounter()`);
mace uses `SwingCounter.maceCounter()`, which computes the magnitude of the
three gyro axes each sample, keeps a trailing moving average of the last
`GYRO_SMOOTHING_SAMPLES`, and confirms a swing one sample late when the
previous average was a local maximum above `GYRO_THRESHOLD_DPS` and at least
`GYRO_MIN_GAP_SAMPLES` have passed since the last one. All three constants
live in `source/motion/SwingCounter.mc`.

If a device's gyroscope registration fails (see `WorkoutSession.startMotionCapture`),
mace falls back to the accelerometer detector it used before gyro-primary
counting shipped, rather than silently counting zero swings.

## Current constants and their evidence

As of this writing: `GYRO_THRESHOLD_DPS = 250.0`, `GYRO_SMOOTHING_SAMPLES = 22`,
`GYRO_MIN_GAP_SAMPLES = 25`. These are validated against exactly two labelled
recordings with real per-set ground truth (`tools/fixtures/index.json`'s
`recB` and `recC` — see that file's `notes` for what each recording is).
That is a small evidence base; treat these constants as a reasonable first
cut, not a settled result. See [CONTRIBUTING.md](../CONTRIBUTING.md#calibration-recordings)
for how to contribute another labelled recording.

The athlete reported 50-70 swings per set, per arm. Both clubs move together
and the watch counts the wrist it is on, so a per-set count *is* a per-arm
count: 772 across 12 sets, averaging 64, lands inside that range.

**The drop in sets 10-12 is real fatigue, not the detector failing.** Asked
directly, the athlete confirmed being tired by then. That is the more useful
half of this session - a counter that quietly degrades and a counter that
tracks a genuine 30% decline in volume look identical in a total, and only
ground truth separates them. It also says `HIGH_MG = 1700` is placed low
enough to catch tired, softer swings, which is the case it would be expected
to miss. Per-second work peaks that session: median 1682 mg, p90 2456.

This is weaker evidence than `recB` and `recC` above - those carry labelled
per-set counts recorded deliberately, while this is a recollection confirmed
after the fact - and it is stronger than the four unlabelled recordings the
tooling otherwise runs against. Treat it as a field check rather than a
calibration input.

### The Rhythm Score rose as the athlete tired

48/45/42 across the three most fatigued sets, against 39-40 when fresh and
swinging 67-85. Slower, more deliberate swinging genuinely is more evenly
spaced, so the score may be reporting exactly what it measures. But a
practitioner reading 48 on their last set could reasonably take it as their
best, and it was their most exhausted. Unresolved, and recorded here because
the ground truth that raises the question came with it.

## Replay-testing this algorithm against real recordings

Rather than a second, TypeScript reimplementation of the counter that can
drift out of sync with the real `.mc` source (as `tools/tune-swing-counter.ts`'s
constants once did), the app can replay a real recording's raw gyro samples
through the *actual* production `SwingCounter.Counter` inside a Monkey C unit
test:

- `source/motion/RecordedFixtureRecB.mc` / `RecordedFixtureRecC.mc` embed a
  fixture's per-second gyro samples and work/rest phase, generated by
  `tools/export-replay-fixture.ts <fixtureId>` from `tools/fixtures/index.json`.
  They stay at the recording's native ~12.5Hz (decimated 2x at capture time
  to fit the FIT developer-field budget) — fine for regression testing, since
  that only needs a fixed, repeatable input.
- `source/motion/RecordedSwingReplay.mc` feeds those samples through a
  `SwingCounter.Counter` the same way `WorkoutSession.onSensorData` does live,
  and reports the swing count per work set.
- `source/motion/RecordedSwingReplayTest.mc` asserts the result against a
  captured baseline (not the recording's true ground truth — see below) so a
  future algorithm change that moves the count on real data fails CI instead
  of going unnoticed.

All three are `(:test)`-annotated and excluded from every store build.

### Tuning: `make tuning-search`

`source/motion/SwingTuningSearch.mc` runs `SwingCounter.maceCounterWithGyroParams(...)`
(threshold/smoothing/gap made configurable per-instance for exactly this
purpose) across a grid of candidate values against both fixtures, and prints
each combo's error against real ground truth as CSV.

This needs true 25Hz input to mean what `GYRO_SMOOTHING_SAMPLES`/`GYRO_MIN_GAP_SAMPLES`
mean in production - the committed fixtures' native ~12.5Hz decimation would
silently double the effective window/refractory time a search sees. So the
search runs against a separate, higher-fidelity fixture reconstructed by
linearly interpolating the recorded samples back to 25Hz:

```sh
node --experimental-strip-types tools/export-replay-fixture.ts recB --resample25hz
node --experimental-strip-types tools/export-replay-fixture.ts recC --resample25hz
make format
make tuning-search
```

The `*Tuning.mc` files this writes are gitignored and dev-local (interpolation
roughly doubles the sample count, which pushes recC's generated file past the
1 MiB pre-commit limit) - regenerate them before running the search rather
than expecting them to already exist. `swingTuning` is excluded from every
other build, so this never runs as part of `make check` or CI.

### Finding (2026-08-29): current constants are close to optimal, not settled

Running the corrected (true-25Hz) search found the shipped constants score
`recB` exactly (`[5, 5, 10, 10]`, matching ground truth) and `recC` within 5
of exact (`[55, 60]` vs `[60, 60]`). A single change - narrowing
`GYRO_SMOOTHING_SAMPLES` from 22 to 19, leaving threshold and gap alone -
reproduces both recordings exactly, and sits inside a broad band of
similarly-good smoothing/gap combinations rather than an isolated spike,
which is some evidence against it being a pure overfit.

That said, "exact" here means "exactly fits the only two labelled recordings
that exist," which is a real overfitting risk on N=2. **Decision: leave the
constants as they are and do not adopt this change** until more labelled
recordings exist - specifically the metronome ground-truth recordings
(fixed BPM, swing-on-beat, giving exact per-rep timing instead of per-set
totals) that are still pending. Re-run `make tuning-search` once those land;
if the same narrower window still wins across a larger, more diverse set of
recordings, it's a real finding rather than a two-point fit.
